# 一生账本 P0 / P1 数据与计算内核实现说明

> 对应产品文档 v2.0。本文描述代码中的确定性内核，不定义页面样式。

## 1. 模块边界

正式内核分为两层：

- `src/features/life-ledger/domain/`：P0 唯一数据标准、校验、总额替代和迁移。
- `src/features/life-ledger/calculation/monthly.ts`：P1 月度计算、年度汇总、所需收入反推和结果追溯。

旧的 `calculation/calculate.ts` 仍作为 Landing Page 原型的兼容层。正式工作台不得继续扩展旧的年度输入模型，应通过 `createQuickLifePlan` 将首页数据转换为 P0 计划，再调用 `calculateMonthlyLifePlan`。

## 2. P0 数据标准

### 2.1 单位

- 金额：整数分 `MoneyCents`，人民币 1 元存为 100。
- 时间：整数月份 `MonthIndex = year * 12 + month - 1`。
- 时间区间：开始月包含、结束月不包含 `[startMonth, endMonthExclusive)`。
- 利率：整数基点 `BasisPoints`，100 基点等于 1%。
- 购买力：当前版本固定为 `today`，即按今天的购买力。

### 2.2 计划结构

`LifePlan` 是页面、存储、计算、导出和未来 Agent 的唯一事实来源，包含：

- 基本时间、主成员和家庭成员。
- 收支桶和独立收支。
- 流动与非流动资产。
- 房贷及其他显式债务。
- 计算假设、数据版本、计算版本和元数据。

每笔现金流都包含金额、频率、分类、归属、起止月份、增长率、来源和确认状态。Agent 建议未确认时校验失败，不能进入正式计算。

### 2.3 总额替代规则

每个 `CashFlowBucket` 只能处于一种模式：

1. `summary`：只计算概括金额。
2. `detailed` 且明细小于概括金额：只计算明细，并临时生成“待分类”差额。
3. `detailed` 且明细等于概括金额：只计算明细。
4. `detailed` 且明细超过概括金额：必须确认新的明细合计，否则阻止计算。

“待分类”只存在于解析结果，不回写原始计划。`ResolutionTrace` 记录排除的概括项、纳入的明细项和生成的差额项，因此同一笔钱不会同时以总额和明细进入计算。

### 2.4 数据校验

`validateLifePlan` 返回带字段路径、错误码、严重级别、文案键和恢复建议的结构化问题。当前覆盖：

- schema、整数金额、利率与月份范围。
- 成员归属、ID 唯一性和来源完整性。
- Agent 建议确认状态。
- 总额与明细冲突。
- 退休月份和计划范围。

### 2.5 迁移

`migrateLifePlan` 是纯函数，由调用方传入计划 ID 和时间，不读取 `Date` 或浏览器状态。当前支持：

- P0 `2.0.0` 计划的验证读取。
- 旧 Landing 年度输入或 `1.0.0` 输入迁移为 `2.0.0`。
- 不认识的未来版本明确失败，不猜测字段。

## 3. P1 月度计算

### 3.1 固定计算顺序

每个月按同一顺序处理：

1. 读取月初可用资金、非流动资产和债务本金。
2. 计算可用资金收益或资金缺口成本。
3. 投放当月、当年或一次性收入与支出。
4. 投放反推收入的工作期补充额（仅求解场景）。
5. 对显式债务计息并执行不超过剩余本息的还款。
6. 对非流动资产按月计提价值变化。
7. 计算月末可用资金、债务和净资产。

所有金额在每次月度入账时四舍五入为整数分，负数采用关于零点对称的舍入方式。

### 3.2 资产口径

- 可用资金：流动资产期初值及此后的现金流变化。
- 债务：显式负债剩余本金和当月利息，不用负现金伪装新债务。
- 非流动资产：房产等资产单独增长，不作为可用现金。
- 净资产：可用资金 + 非流动资产 - 债务。

因此，拥有房产不会让“可用资金”虚增；中途现金为负即视为资金缺口，即使最终净资产或期末现金为正。

### 3.3 输出

`calculateMonthlyLifePlan` 返回：

- 每月账本和逐条 `traceIds`。
- 只由月度账本聚合得到的年度记录。
- 首次缺口月/年、最低可用资金、期末可用资金、退休时可用资金。
- 期末债务与净资产。
- “期末归零”和“全程不缺钱”两套月收入要求。
- 对期末可用资金影响最大的三项输入（统一做金额增加 10% 的敏感性比较）。
- 输入摘要、输入哈希、计算版本、数据版本和替代规则追溯。

失败使用 `safeCalculateMonthlyLifePlan` 返回结构化错误，不返回部分月度结果。

## 4. 首页到正式计划的调用约定

P2 接入时应采用以下流程：

1. Landing 继续只收集少量总额。
2. 点击按钮后用 `createQuickLifePlan` 转为完整 `LifePlan`。
3. 将完整计划写入 `sessionStorage`，URL 只跳转到 `/plan`，不携带财务参数。
4. `/plan` 读取并校验计划，先写入 IndexedDB 草稿，再清除临时交接数据。
5. 正式结果只调用 `calculateMonthlyLifePlan`。
6. 缓存键使用 `inputHash + calculationVersion + dataVersion`。

旧 `/plans/new` 和旧年度计算结果属于兼容原型，不应成为新页面依赖。

## 5. 测试和放行

`npm run test:calculation` 当前同时执行：

- P0 总额替代、超额确认、Agent 确认和迁移测试。
- P1 公式与守恒测试。
- 11 个黄金输入：单身租房、已有住房、房贷、伴侣、孩子、父母、提前退休、工作中断、一次性支出、中途缺口、总额拆分。
- 月度与年度聚合一致性。
- 可用资金、债务和房产的口径分离。
- 固定种子的随机确定性、有限数值和输入不可变测试。
- 旧 Landing 兼容回归测试。

自动测试通过不等于人工金额复核。进入 P2 正式工作台前，产品负责人仍需逐项签署 `golden-fixtures.ts` 中的预期值，尤其是含利率、跨年和房贷的案例。
