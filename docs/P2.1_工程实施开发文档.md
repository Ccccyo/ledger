> 状态：开发中（阶段 0–2 已验收；阶段 3–7 已实现，补充跨阶段验收；阶段 8 收尾中）

## 1. 开发目标

本阶段把现有“快速计算器 + 基础工作台”升级为一条完整的个人长期规划流程：

```text
Landing 填写 7 个个人数据
  → 建立个人基线
  → 工作台补充资产明细与人生事件
  → 查看人生轨迹与两张核心图表
  → 阅读确定性系统分析
  → 无损试算一个调整
  → 确认后应用到正式计划
  → 在年度账本核对结果
```

交付完成后，即使断网、未配置 AI 或删除全部 AI 服务，用户仍能完成以上流程。

## 2. 工程红线

### 2.1 正式数字只有一个来源

正式金额只能来自：

```ts
calculateMonthlyLifePlan(plan: LifePlan): MonthlyCalculationResult
```

页面组件、系统分析和方案试算不得自行实现另一套金额公式。允许组件做格式化、筛选和展示聚合，不允许重新计算现金流、贷款、收益或缺口。

### 2.2 不接入 AI

P2.1 不调用以下目录或服务：

- `src/extensions/ai/`
- `src/shared/services/ai.ts`
- `/api/ai/*`
- Chat、模型选择器、Prompt 或 Agent API

`analysis/` 必须是纯 TypeScript 模块，无网络、浏览器、React 和 AI SDK 依赖。

### 2.3 不改动正式计算语义

除年度结果补充年龄字段等只读输出外，P2.1 不重写 P1 月度顺序。需要新增产品能力时优先通过构造 `LifePlan`、提取正式结果或重算计划副本实现。

后续用户明确增加职业发展：当前工资实际增长、换工作、副业、暂停工作。为防止新旧工资重复相加，已增加受校验的个人工资替换标记；停工可覆盖换工作区间，但同类覆盖不能重叠。月度规则版本因此更新，其他收支、资产和债务的计算顺序不变。工资增长仍由同一月度计算内核处理。

### 2.4 不提前开发排除项

不开发城市数据库、自动房价、教育路线、养老金政策、三情景、多方案管理、CSV、公式审计和真实数据自动抓取。任何未完成的 AI/Agent 能力不显示入口。

## 5. 核心数据契约

### 5.1 Landing 输入

```ts
interface PersonalBaselineInput {
  currentAge: number;
  startingAvailableAssetsWan: number;
  monthlyIncomeYuan: number;
  monthlyExpenseYuan: number;
  monthlyRetirementSelfFundedYuan: number;
  retirementAge: number;
  endAge: number;
}
```

字段合同：

| 字段                              |              范围 | 默认值 | 含义                                   |
| --------------------------------- | ----------------: | -----: | -------------------------------------- |
| `currentAge`                      |            18～75 |     28 | 当前年龄                               |
| `startingAvailableAssetsWan`      |        0～100,000 |      0 | 可用于长期规划的存款和现金，单位“万”   |
| `monthlyIncomeYuan`               |     0～10,000,000 | 18,000 | 个人当前税后月收入                     |
| `monthlyExpenseYuan`              |     0～10,000,000 |  9,000 | 工作期个人每月支出                     |
| `monthlyRetirementSelfFundedYuan` |     0～10,000,000 |  7,000 | 扣除养老金等稳定收入后，退休每月需自付 |
| `retirementAge`                   |  当前年龄 + 1～80 |     60 | 个人收入停止年龄                       |
| `endAge`                          | 退休年龄 + 1～120 |     90 | 计算终点年龄                           |

Landing 不接收家庭结构、伴侣、孩子、父母、非流动资产、债务或养老金政策；接收一项以“万”为单位的起始可用资产估算，以及用户估算的退休后每月需自付金额。

### 5.2 Landing 到正式计划的映射

新增纯函数：

```ts
function createPersonalBaselinePlan(
  input: PersonalBaselineInput,
  context: {
    id: string;
    baseMonth: MonthIndex;
    nowIso: string;
  }
): LifePlan;
```

映射规则：

| 正式字段            | Landing 映射                                            |
| ------------------- | ------------------------------------------------------- |
| `members`           | 只创建 `self`                                           |
| `baseMonth`         | 由页面显式传入当前月，工厂函数不读取系统时间            |
| `retirementMonth`   | 根据当前年龄和退休年龄计算                              |
| `endMonthExclusive` | 根据当前年龄和终点年龄计算                              |
| 收入 bucket         | 个人月收入，从 `baseMonth` 到 `retirementMonth`         |
| 工作期支出 bucket   | 个人月支出，从 `baseMonth` 到 `retirementMonth`         |
| 退休期支出 bucket   | 用户填写的退休后每月需自付，从 `retirementMonth` 到终点 |
| 资产                | `startingAvailableAssetsWan × 10,000` 元，作为流动现金  |
| 负债                | 空数组                                                  |
| 收益假设            | 实际收益率 0%                                           |
| 收入/支出增长       | 实际变化 0%                                             |

必须通过测试证明工作期支出和退休期支出在退休边界不重叠、不遗漏。

### 5.3 年度年龄

当前 `AnnualLedgerRow` 没有年龄字段。为避免 UI 用年份反推年龄，扩展只读结果：

```ts
interface AnnualLedgerRow {
  year: number;
  ageStart: number | null;
  ageEnd: number | null;
  // 保留现有字段
}
```

年龄从该年第一条和最后一条月度记录读取。余额图按年末余额对应 `ageEnd`，详情显示年龄范围；出生月缺失时只显示年份。

### 5.4 人生轨迹

```ts
type LifeStage = 'now' | 'career' | 'partner' | 'child' | 'housing' | 'parents' | 'retirement';

interface LifeTrajectoryNode {
  id: string;
  stage: LifeStage;
  status: 'missing' | 'complete' | 'not-applicable';
  month: MonthIndex | null;
  age: number | null;
  titleKey: string;
  summaryValues: Record<string, string | number>;
  annualImpactCents: MoneyCents | null;
  targetSection: string;
  targetInputId?: string;
}
```

节点名称固定为：

```text
现在 → 职业发展 → 伴侣 → 孩子 → 住房 → 父母 → 退休
```

节点只从 `LifePlan` 和正式结果提取，不单独保存第二份时间轴数据。

### 5.5 系统分析

使用产品设计说明中定义的 `PlanInsight`、`ActionCandidate` 和 `SimulationComparison`。补充版本：

```ts
export const ANALYSIS_VERSION = '1.0.0';
```

系统分析缓存键：

```text
inputHash + calculationVersion + analysisVersion
```

第一版可先不持久化缓存；结果在内存中 `useMemo` 生成。不得把 insight 或 action 写入 `LifePlan`。

### 5.6 白名单计划补丁

不允许通用 JSON Patch。第一版只支持：

```ts
type PlanPatch =
  | {
      type: 'shift-cash-flow';
      cashFlowId: string;
      monthDelta: number;
    }
  | {
      type: 'change-cash-flow-amount';
      cashFlowId: string;
      amountCents: MoneyCents;
    }
  | {
      type: 'change-retirement-month';
      retirementMonth: MonthIndex;
    }
  | {
      type: 'change-liquid-opening-balance';
      assetId: string;
      openingBalanceCents: MoneyCents;
    };
```

每种 patch 使用独立纯函数，校验目标存在、值域合法、时间仍在计划范围内。应用后必须执行 `validateLifePlan`，再调用 P1。

### 6.1 Landing

#### 输入区

- 删除模式切换。
- 删除旧双模式中的存款字段，改为语义明确的“起始可用资产（估算）”。

### 7.2 可用资金与净资产图

数据源：

- `closingAvailableCents`。
- `closingNetWorthCents`。

## 8. 系统分析实现

### 8.1 事实提取

`extractPlanFacts(plan, result)` 至少返回：

```ts
interface PlanFacts {
  firstGapMonth: MonthIndex | null;
  minimumMonth: MonthIndex;
  minimumAvailableCents: MoneyCents;
  endingAvailableCents: MoneyCents;
  endingNetWorthCents: MoneyCents;
  retirementMonth: MonthIndex;
  largestExpenseYear: number | null;
  largestExpenseCategories: CashFlowCategory[];
  eventWindows: EventWindow[];
  missingSections: LifeStage[];
  topInfluences: InfluenceResult[];
}
```

事实提取只读取数据，不生成文案和行动。

### 8.2 第一批规则

按以下顺序实现：

1. `housing-causes-first-gap`：购房前后 12 个月出现首次缺口。
2. `housing-child-overlap`：购房与孩子支出在 24 个月内重叠。
3. `liquidity-gap`：可用资金为负但同期净资产为正。
4. `retirement-transition-gap`：停止工作后、稳定退休收入开始前出现缺口。
5. `retirement-spend-sensitive`：退休支出进入前三影响因素。
6. `zero-return-conservative`：长期正余额且实际收益率为 0。
7. `important-total-unclassified`：关键分类仍使用总额估算。
8. `baseline-sustainable`：无缺口且主要资料完整。

每条规则一个稳定 `ruleId`，一个测试文件中的至少三个用例：命中、边界、不命中。

### 8.3 原因验证

规则不能只因某项金额最大就写“主要原因”。需要调用统一验证器：

```ts
verifyCause({ plan, baseline, patch }): CauseEvidence
```

验证器对计划副本应用控制变量 patch，重新调用 P1，并返回首次缺口、最低余额和期末余额差值。只有差值达到规则阈值时，文案才使用“主要触发因素”；否则降级为“与该阶段同时发生”。

### 8.4 排序与数量

- `gap` 高于 `attention`，`attention` 高于 `info`。
- 能解释首次缺口的规则优先。
- 有可执行 patch 的规则优先。
- 相同输入字段的重复规则保留证据更强的一条。
- 页面最多显示 3 条 insight 和 3 个 action。

## 9. 方案试算实现

### 9.1 状态

```ts
type SimulationState =
  | { status: 'closed' }
  | {
      status: 'editing';
      baselineHash: string;
      action: ActionCandidate;
      draftPatch: PlanPatch;
      lastValidComparison?: SimulationComparison;
      error?: string;
    }
  | {
      status: 'ready';
      baselineHash: string;
      action: ActionCandidate;
      comparison: SimulationComparison;
    }
  | { status: 'stale'; reason: 'baseline-changed' };
```

该状态仅保存在内存中，不进入 IndexedDB、URL 或备份。

### 9.2 重算

```ts
function simulateAction(
  baselinePlan: LifePlan,
  baselineResult: MonthlyCalculationResult,
  patch: PlanPatch
): SimulationResult;
```

固定顺序：

1. 深复制或不可变更新正式计划。
2. 应用白名单 patch。
3. P0 校验候选计划。
4. P1 计算候选结果。
5. 生成 `ResultDigest`。
6. 返回基线、候选和差值。

### 9.3 应用

点击“应用到计划”时：

1. 再比较当前 `inputHash` 与 `baselineHash`。
2. 不一致则进入 stale，不允许应用旧候选。
3. 一致则把 `candidatePlan` 提交给工作台 reducer。
4. 触发现有自动保存和 revision 检查。
5. 提供一次“撤销本次应用”，撤销内容来自应用前的内存副本。

放弃试算不得触发保存，不得增加 revision。

## 10. 工作台状态重构

当前 `plan-workspace-client.tsx` 同时承担启动、存储、计算、导航和全部 UI。实施 P2.1 前先抽出状态层：

```ts
interface WorkspaceState {
  boot: BootState;
  plan: LifePlan | null;
  result: MonthlyCalculationResult | null;
  saveStatus: 'saved' | 'saving' | 'failed' | 'stale';
  calculationStatus: 'idle' | 'calculating' | 'failed';
  lastChange?: ResultDelta;
  simulation: SimulationState;
  drawer: DrawerState;
}
```

职责：

| 层         | 职责                                    |
| ---------- | --------------------------------------- |
| Provider   | 连接 repository、计算器、广播和 reducer |
| Reducer    | 纯状态转换，不访问浏览器 API            |
| Views      | 消费状态、派发用户意图                  |
| Repository | IndexedDB 和 revision                   |
| Analysis   | 读取正式 plan/result，生成派生内容      |

保存与计算仍保持：字段合法后重算，计算成功后再保存；失败时保留上一次有效结果。
