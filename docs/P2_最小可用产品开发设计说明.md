# 一生账本 P2 最小可用产品开发设计说明

> 状态：开发基线  
> 依赖：P0 数据标准与 P1 月度计算内核  
> 目标：用户不使用 AI，也能创建、理解、修改、保存和核对一份家庭长期收支计划

> 后续产品动线补充：`P2.1_真实用户动线与系统分析开发设计说明.md`。在工作台导航、人生轨迹、两张核心图表、确定性系统分析和方案试算方面以 P2.1 为准；本文的存储、恢复、隐私、计算可靠性和基础工程约束继续有效。

## 1. 目标与结论

P2 将当前“Landing 页计算器加结果展示原型”升级为可长期使用的本地计划工具。普通用户只接触两个页面：Landing Page `/` 和计划工作台 `/plan`。Landing 只用当前个人收支建立快速基线；工作台负责补充人生事件、解释结果，并在概览内按需展开逐年账本。

P2 的关键产品决定如下：

| 主题         | P2 决定                                                   |
| ------------ | --------------------------------------------------------- |
| 正式计算     | 全部使用 `calculateMonthlyLifePlan`，不再扩展旧年度计算器 |
| 正式数据     | 全部使用 P0 `LifePlan 2.0.0`                              |
| 页面         | 只保留 `/` 与 `/plan` 两个用户页面                        |
| 工作台导航   | 概览、计划两个视图；账本在概览中折叠展示                  |
| 本地存储     | `sessionStorage` 只做临时交接，IndexedDB 保存正式计划     |
| URL          | 只保存安全的界面状态，不出现收入、存款、家庭信息或计划 ID |
| 结果更新     | 有效输入停止 400ms 后重算；无效输入保留上一次有效结果     |
| 多标签页     | 使用修订号和 `BroadcastChannel` 检测冲突，不静默覆盖      |
| 规划 Agent   | P2 不展示未完成入口，P3 启用现有预留位置                  |
| 方案对比     | P2 不展示，P3 与规划 Agent 一起开发                       |
| 账户与云同步 | 不开发；P2 是单设备、单计划、本地优先产品                 |

P2 不修改 P0/P1 公式。页面只能组装和修改 `LifePlan`，金额结果只能来自确定性计算内核。

开始制作依赖金额结论的概览和账本前，P0/P1 黄金案例需要完成人工签署。存储、路由和无结果的工作台框架可以先并行开发，但不得用旧年度结果临时代替 P1 结果上线。

## 2. 范围

### 2.1 P2 必须完成

- Landing 快速估算改用 P0/P1 正式模型。
- Landing 到 `/plan` 的安全交接。
- 无计划、导入中、可用、损坏和恢复五类启动状态。
- 概览、计划两个主视图，账本在概览内折叠。
- 总额进入工作台后的分类拆分和“待分类”处理。
- IndexedDB 自动保存、快照、备份导出和恢复导入。
- 多标签页冲突提示。
- 中文、英文文案完整对齐。
- 桌面、平板和移动端布局。
- 键盘操作、读屏提示、减少动态效果和图表表格替代。
- 单元、集成、端到端、可访问性和迁移测试。

### 2.2 P2 不开发

- 规划 Agent 与自然语言修改。
- 数据 Agent、数据抓取和数据审核后台。
- 临时方案对比。
- 账户、登录、云同步、团队协作和商业化。
- 自动养老金预测、城市政策推断和投资建议。
- P5 中住房、教育、养老金等模块的专业规则。

住房、孩子、父母、养老金在 P2 中只作为明确的收入、支出、资产和债务记录，不提供自动政策推算。

## 3. 路由与导航

### 3.1 用户路由

| 路由                             | 用途                         |
| -------------------------------- | ---------------------------- |
| `/`                              | 产品说明、快速估算、进入计划 |
| `/plan`                          | 创建状态或当前计划工作台     |
| `/plan?tab=overview`             | 概览，默认值                 |
| `/plan?tab=plan`                 | 编辑计划                     |
| `/plan?tab=plan&section=housing` | 打开住房分组                 |

Next.js 实际路由由 `next-intl` 添加可选语言前缀，例如 `/zh/plan` 和 `/en/plan`。业务代码只通过项目的国际化导航组件生成 URL。

允许进入 URL 的字段只有：

- `tab`：`overview | plan`。
- `section`：计划分组的固定枚举。
- `year`：位于计划范围内的四位年份。
- `focus`：`gap` 等固定界面焦点枚举。

未知、越界或不支持的查询值直接归一化为默认状态，不进入错误页面。

以下内容禁止进入 URL、页面标题和分析事件：

- 收入、支出、存款、资产和债务金额。
- 年龄、退休年龄、家庭成员和城市。
- 计划数据、结果摘要和本地计划 ID。

### 3.2 旧路由迁移

`/[locale]/plans/new` 变为兼容迁移入口，不再展示正式页面：

1. 客户端检查旧 `localStorage` 草稿。
2. 找到时迁移为 `LifePlan 2.0.0`，写入 P2 临时导入区。
3. 导航到 `/plan`。
4. `/plan` 成功写入 IndexedDB 后删除旧草稿。
5. 没有旧草稿时直接导航到 `/plan` 创建状态。

迁移不能在写入成功前删除旧数据。兼容入口保留一个发布周期，之后再删除。

### 3.3 工作台导航

桌面端：顶部栏下方显示“概览、计划”两个水平标签。移动端：底部固定显示两个导航项。逐年账本位于概览底部，默认折叠。

切换标签只改变工作台视图，不重新加载计划，也不重新初始化计算器。浏览器返回键可以恢复上一个标签或打开的年份。

## 4. Landing Page

### 4.1 页面顺序

Landing Page 只保留：

1. Hero 与快速计算器。
2. 快速结果。
3. 三步说明：填写、计算、调整。
4. 可信说明：计算口径、数据来源、本地保存边界。
5. 简洁页脚：隐私政策、服务条款、语言和主题。

隐藏定价、登录、博客、通用 AI、案例市场、积分和脚手架入口。

### 4.2 快速计算器

Landing 只建立个人基线，不出现家庭结构、伴侣、孩子或父母输入，也不提供“按目标生活反算收入”模式。

使用以下 7 个字段：

| 字段             | 单位  | 输入限制                   |
| ---------------- | ----- | -------------------------- |
| 当前年龄         | 岁    | 18～75，整数               |
| 起始可用资产估算 | 万    | 非负数，只含可用存款和现金 |
| 个人税后月收入   | 元/月 | 非负数                     |
| 工作期个人月支出 | 元/月 | 非负数                     |
| 退休后每月需自付 | 元/月 | 非负数                     |
| 计划退休年龄     | 岁    | 大于当前年龄，最大 80      |
| 计算终点年龄     | 岁    | 大于退休年龄               |

输入框内部保留字符串，提交时一次性转换为整数分。禁止在用户还在输入 `1.` 或清空字段时强制转成 `0`。

Landing 只接收一项起始可用资产估算，不填写非流动资产、债务或养老金政策。用户以“万”为单位录入，提交时显式换算为整数元，再由正式模型转换为整数分；退休前使用个人收入与工作期支出，退休后个人收入按 0 处理，支出使用用户填写的每月需自付金额。该金额应扣除预计养老金等稳定退休收入。用户进入工作台后再补充可单独追溯的资产、退休收入与支出和其他人生事件。

### 4.3 快速估算的公开假设

Landing 输入有限，因此结果区域必须直接显示以下假设，不能隐藏在 tooltip：

- 规划终点由用户填写，默认 90 岁。
- 计划起点取用户点击计算时的当前月份；计算内核本身不读取系统时间。
- Landing 只有当前年龄，因此暂按计划起始月推算出生月份；工作台可以补充准确出生年月。
- Landing 暂按退休后没有单列个人收入处理，支出使用用户填写的退休后每月需自付金额。
- 暂不预测养老金；用户在 Landing 以扣除预计养老金等稳定收入后的自付金额输入，进入工作台后可再拆分退休收入与支出。
- Landing 以用户估算的起始可用资产起算；用户可以在工作台补充资产明细和债务。
- 暂不计入房产、房贷、孩子、父母和一次性事件。
- 暂按今天的购买力计算，默认实际收益率为 0。

假设文案应放在快速结果下方的紧凑说明中，并提供“在计划中修改”的入口。

### 4.4 计算与结果

用户点击“查看结果”后：

1. 校验 7 个个人字段及年龄顺序。
2. 调用 `createQuickLifePlan` 生成完整 P0 计划。
3. 调用 `safeCalculateMonthlyLifePlan`。
4. 成功时平滑滚动到结果区；遵守 `prefers-reduced-motion`。
5. 失败时将焦点移到首个错误字段，不移动到结果区。

输入在上次计算后发生变化时，结果区域显示“输入已修改，请重新计算”，并暂时禁用“完善我的一生账本”，防止把旧结果和新输入组合后带入工作台。

快速结果只展示：

- 一句条件式结论。
- 首次缺口时间。
- 计算终点可用资金。

结论示例：

- “按照当前输入，规划期内暂未出现资金缺口。”
- “按照当前输入，预计在 2058 年 7 月首次出现资金缺口。”
- “虽然规划终点仍有结余，但中间预计会在 2032 年 3 月出现资金缺口。”

结果下方固定显示：

> 这是基于个人起始资产与当前收支的快速估算。补充住房、伴侣-孩子、父母和退休收入后，结果会更完整。

主操作是“完善我的一生账本”，次操作是“重新估算”。

### 4.5 Landing 到工作台的交接

点击“完善我的一生账本”执行：

1. 生成随机计划 ID。
2. 将当前快速输入转为 `LifePlan 2.0.0`。
3. 再执行一次 P0 校验。
4. 写入 `sessionStorage` 的 v2 交接信封。
5. 导航到 `/plan`，URL 不携带金额或计划 ID。

交接信封：

```ts
interface QuickPlanHandoffV2 {
  envelopeVersion: '2.0.0';
  source: 'landing-quick-estimate';
  createdAt: number;
  expiresAt: number;
  plan: LifePlan;
  inputHash: string;
}
```

存储键为 `life-ledger.quick-handoff.v2`，有效期 30 分钟。读取时同时校验信封、过期时间、计划 schema 和输入哈希。

## 5. `/plan` 启动流程

### 5.1 启动优先级

工作台首次加载按以下顺序处理：

1. 打开 IndexedDB。
2. 读取当前活动计划。
3. 检查 v2 Landing 交接。
4. 检查 v1 Landing 交接与旧 `localStorage` 草稿。
5. 根据是否存在正式计划和待导入计划决定启动状态。

不得先清除 sessionStorage，再尝试 IndexedDB 写入。

### 5.2 启动状态

| 状态                | 展示与操作                                               |
| ------------------- | -------------------------------------------------------- |
| `loading`           | 骨架屏和“正在读取本机计划”                               |
| `empty`             | 创建第一份计划，可返回 Landing 或从备份导入              |
| `importing`         | 正在将 Landing 结果写入 IndexedDB                        |
| `ready`             | 进入工作台上次视图，默认概览                             |
| `recoverable-error` | 数据损坏，可恢复快照、导入备份或重新创建                 |
| `unavailable`       | 浏览器不支持或拒绝 IndexedDB，说明限制并允许导出临时数据 |

### 5.3 新交接与已有计划

第一版只支持一个活动计划。用户从 Landing 明确点击“完善账本”后，本次估算直接更新当前活动计划，不再展示额外冲突确认页。

更新必须在一个事务内先保存旧计划快照，再写入新计划和活动计划索引；事务失败时旧计划保持不变。多浏览器标签页的并发编辑冲突仍按修订号处理。

### 5.4 成功导入

一个 IndexedDB 事务完成以下写入：

1. `plans` 写入正式计划。
2. `snapshots` 写入第 1 个快照。
3. `meta` 写入活动计划 ID。

事务成功后才清除 v2/v1 sessionStorage 和已迁移旧草稿。随后使用 `router.replace('/plan?tab=overview')`，防止刷新重新触发导入。

## 6. 工作台全局结构

### 6.1 顶部栏

顶部栏高度桌面端 64px，显示：

- 一生账本品牌，点击回到 Landing。
- 当前计划名称，可从更多菜单重命名。
- 保存状态。
- “按今天的钱计算”。
- 更多菜单。

P2 不显示规划 Agent 按钮。P3 启用后放在“更多”左侧，桌面打开右侧面板，移动端打开全屏面板。

更多菜单包含：

- 重命名计划。
- 导出备份。
- 导入备份。
- 恢复最近快照。
- 删除并重新创建。

删除必须使用明确的确认对话框，说明本地数据将被删除，并在删除前提供导出备份。

### 6.2 标签与内容宽度

- 桌面最大内容宽度 1200px。
- 概览采用单列主叙事，指标区域最多四列。
- 计划视图最大阅读宽度 920px，避免表单横向过散。
- 账本可使用 1200px 宽度容纳表格。
- 页面不使用常驻侧边栏。

桌面标签位于顶部栏下方并保持粘性。移动端底部导航高度 56px，加上 `env(safe-area-inset-bottom)`。

### 6.3 保存状态

顶部栏只使用以下文案：

- 保存中。
- 已自动保存。
- 保存失败。
- 结果待更新。
- 当前显示上一次有效结果。

状态规则：

| 条件               | 显示                   |
| ------------------ | ---------------------- |
| 本地计划与表单一致 | 已自动保存             |
| 正在写入 IndexedDB | 保存中                 |
| 输入暂时无效       | 结果待更新             |
| 计算失败且有旧结果 | 当前显示上一次有效结果 |
| IndexedDB 写入失败 | 保存失败               |

保存失败状态必须提供“重试”和“导出当前数据”，不能只显示红色图标。

## 7. 概览视图

### 7.1 内容顺序

1. 一句话结论。
2. 四个核心指标。
3. 主要资金曲线。
4. 三个主要影响因素。
5. 数据完整性提示。
6. “修改计划”操作。

不放营销卡、功能推荐、登录提示或 Agent 占位卡。

### 7.2 结论生成

结论必须同时判断中途与终点：

| 中途缺口 | 终点可用资金 | 结论重点                       |
| -------- | -----------: | ------------------------------ |
| 否       |   大于等于 0 | 规划期内暂未出现缺口           |
| 是       |       小于 0 | 首次缺口时间与规划终点缺口     |
| 是       |   大于等于 0 | 最终有结余，但中间出现资金中断 |

所有结论以“按照当前输入”开头，不使用“你一定”“保证”“准确率”等表述。

### 7.3 四个核心指标

| 指标                 | 显示规则                             |
| -------------------- | ------------------------------------ |
| 资金是否中断         | “暂未出现”或“预计会出现”             |
| 首次缺口             | `YYYY 年 M 月`，无缺口时显示“—”      |
| 最低可用资金         | 人民币，负数使用负号，不用“欠款”代替 |
| 全程不缺钱所需月收入 | 使用 P1 `noGapMonthlyIncomeCents`    |

规划终点可用资金放在结论补充文字中，不再制作第五张同级卡片。

金额统一右对齐并使用等宽数字。超过一百万元时仍保留完整值；可在次级文本显示“约 120 万元”，但完整金额必须可读。

### 7.4 资金曲线

默认显示三条：

- 可用资金。
- 债务余额。
- 净资产。

横轴按年，数据来自 P1 年度聚合。首次缺口年份使用琥珀色竖线标记。悬停或键盘聚焦显示该年精确数值。

图表下方提供“查看表格数据”，显示相同数据的可访问表格。图表不承载独有信息。

### 7.5 主要影响因素

使用 P1 `topInfluences`，展示：

- 输入名称。
- 统一扰动口径“金额增加 10%”。
- 对终点可用资金的变化方向和金额。

文案必须称为“敏感性影响”，不描述为因果推断。

### 7.6 数据完整性

只显示以下三级：

| 等级           | 判定                                                           |
| -------------- | -------------------------------------------------------------- |
| 基础估算       | 只有 Landing 总额或主要分类仍为概括模式                        |
| 已补充主要信息 | 收入、生活、住房、退休四组已确认，且没有待确认 Agent/外部值    |
| 详细计划       | 所有非零总额均已拆分或明确选择保留总额，关键资产和债务均有来源 |

不显示百分比。完整性提示列出最多三项最值得补充的信息，并链接到计划分组。

## 8. 计划视图

### 8.1 固定摘要

计划视图顶部固定显示：

- 当前月收入。
- 当前月总支出。
- 已分类支出。
- 待分类支出。
- 当前可用资金。

“当前月”统一指计划 `baseMonth`。年度和一次性项目不强行折算进当前月摘要，在对应分组单独显示。

### 8.2 分组结构

一次只展开一个分组：

| 分组       | P2 字段                                          |
| ---------- | ------------------------------------------------ |
| 基本情况   | 出生年月或当前年龄、计划起点、退休月份、规划终点 |
| 收入与工作 | 工资、副业、伴侣收入、养老金、工作中断时间       |
| 日常生活   | 每月生活总额或生活明细                           |
| 住房       | 租金/物业支出、房产、房贷                        |
| 伴侣-孩子  | 伴侣、孩子及相关现金流                           |
| 父母       | 父母成员及赡养支出                               |
| 退休       | 退休后个人需承担支出、养老金收入                 |
| 人生事件   | 一次性收入和支出、开始与结束月份                 |
| 高级设定   | 实际收益率、资金缺口成本、现金流增长率           |

P2 不自动计算城市房价、教育成本或养老金。用户可以手动记录金额，并看到“用户填写”来源。

### 8.3 折叠项摘要

折叠状态只显示：

- 分类名称。
- 当前概括金额。
- 数据来源。
- “已填写”“有待分类”“需要补充”状态。
- 展开按钮。

不得在折叠行同时放置多个编辑按钮。整行和右侧箭头均可展开，使用原生按钮和 `aria-expanded`。

### 8.4 总额与明细编辑

概括模式：

- 显示一个总额输入。
- 解释“先使用总额估算，可以稍后拆分”。
- “拆分明细”切换到详细模式。

详细模式：

- 概括总额作为参考，不进入计算。
- 显示明细合计、待分类和原概括总额。
- 明细小于总额时自动显示只读“待分类”。
- 明细超过总额时显示差额和“确认新总额”。
- 用户确认前不替换正式计划，不触发正式结果更新。

从详细模式切回概括模式必须提示：明细仍保留在草稿中，但计算将使用概括总额。用户确认后才切换。

### 8.5 表单提交与计算

每个金额、日期字段维护一个临时字符串值。状态流：

```text
输入中 → 字段解析 → 分组校验 → 计划校验 → 月度计算 → 保存
   └──────── 无效：保留字段值和上一次有效结果 ────────┘
```

具体规则：

- 有效输入停止 400ms 后提交，失焦时立即尝试提交。
- 字段无效时显示紧邻错误，不更新 `LifePlan`。
- 分组有效后生成不可变计划副本。
- 计算请求携带递增 `requestId`，过期结果不覆盖新结果。
- 计算成功后更新结果并进入自动保存队列。
- 计算失败时保留上一次有效结果。
- 输入变化不改变页面高度，不让左侧说明或顶部摘要跳动。

### 8.6 重大变化提示

以下变化显示一次简短差异提示：

- 首次出现或消除资金缺口。
- 首次缺口变化超过一年。
- 所需月收入变化超过 10%。
- 退休月份发生变化。

提示只在计算完成后出现，不在每次键入时闪烁。用户可以关闭，关闭不影响保存。

## 11. 本地数据设计

### 11.1 存储边界

| 存储             | 内容                                   |
| ---------------- | -------------------------------------- |
| `sessionStorage` | Landing 交接、一次性旧数据迁移交接     |
| IndexedDB        | 正式计划、快照、结果缓存、活动计划指针 |
| `localStorage`   | 语言、主题、上次打开的安全界面偏好     |

财务计划不得继续写入 `localStorage`。

### 11.2 IndexedDB

数据库名称：`life-ledger`，初始版本：`1`。

| Store         | Key                                            | 内容                                  |
| ------------- | ---------------------------------------------- | ------------------------------------- |
| `plans`       | `plan.id`                                      | 正式计划、修订号、校验和、保存时间    |
| `snapshots`   | `[planId, revision]`                           | 保存前快照，最多保留最近 10 个        |
| `resultCache` | `[inputHash, calculationVersion, dataVersion]` | 最近一个有效计算结果                  |
| `meta`        | 固定字符串                                     | 活动计划 ID、数据库版本和最后打开时间 |

计划记录：

```ts
interface StoredPlanRecord {
  id: string;
  schemaVersion: '2.0.0';
  revision: number;
  checksum: string;
  plan: LifePlan;
  updatedAt: string;
  writerId: string;
}
```

保存采用 `plans + snapshots + meta` 单事务：

1. 读取当前 revision。
2. 与调用方 `expectedRevision` 比较。
3. 相等时把旧记录写入快照。
4. 写入 revision + 1 的新计划。
5. 更新活动计划指针。
6. 清理超过 10 个的旧快照。

任何一步失败，整个事务回滚。

`resultCache` 只保留活动计划最近一次有效结果；新缓存写入成功后删除同一计划的旧缓存，避免逐月追溯结果无限增长。校验和使用 Web Crypto SHA-256，只用于发现损坏，不描述为加密或安全保护。

### 11.3 自动保存

- 计算成功后等待 500ms 合并连续更新。
- 页面隐藏或离开前立即提交待保存计划。
- 同一时间只允许一个保存事务。
- 新修改发生在保存期间时，当前保存完成后立即保存最新版本。
- 结果缓存失败不影响计划保存。
- 计划保存失败不得清除内存中的修改。

### 11.4 多标签页冲突

每个标签页生成随机 `writerId`，使用 `BroadcastChannel('life-ledger')` 广播：

```ts
type PlanBroadcastMessage =
  | { type: 'plan-saved'; planId: string; revision: number; writerId: string }
  | { type: 'plan-deleted'; planId: string; writerId: string };
```

收到其他标签页更高 revision 时：

- 本页无未保存修改：提示并自动读取新版。
- 本页有未保存修改：进入冲突状态，提供“查看新版”“保留本页副本”“导出本页数据”。
- 不允许最后写入者静默覆盖。

支持 `navigator.locks` 时，用它串行化保存；不支持时仍依赖 revision 比较保证不覆盖。

### 11.5 备份与恢复

导出文件名：`life-ledger-backup-YYYY-MM-DD.json`。

备份内容包含：

- 备份格式版本。
- 完整 `LifePlan`。
- 导出时间。
- schema、计算和数据版本。
- 内容校验和。

不包含计算缓存、主题、语言或浏览器标识。

导入流程必须先解析、迁移、校验和预览，再由用户确认覆盖。导入失败不得改变当前计划。

数据损坏时依次提供：恢复最近有效快照、导入备份、导出原始损坏数据、重新创建。

界面只描述“数据保存在当前浏览器”，不使用“已加密”“绝对安全”等未经证明的表述。

### 12.2 状态职责

`WorkspaceProvider` 只管理：

- 已加载的正式计划。
- 表单临时状态。
- 上一次有效计算结果。
- 当前计算请求状态。
- 保存 revision 与保存状态。
- 冲突和恢复状态。
- 当前打开的抽屉。

URL 管理当前 tab、section、year 和 focus，不在 React Context 重复维护一份真值。

组件禁止直接访问 IndexedDB、sessionStorage 或计算函数。所有副作用通过 repository、handoff service 和 calculation client 执行。

### 12.3 计算 Worker

P1 内核保持无浏览器依赖，通过 Worker 调用：

```ts
type CalculationRequest = {
  type: 'calculate';
  requestId: number;
  plan: LifePlan;
};

type CalculationResponse =
  | { type: 'success'; requestId: number; result: MonthlyCalculationResult }
  | { type: 'failure'; requestId: number; error: MonthlyCalculationErrorShape };
```

主线程只接受最新 `requestId`。Worker 不可用时使用相同接口回退到主线程，并通过 `startTransition` 更新结果。

### 12.4 数据更新顺序

```text
字段临时值
  → 解析与字段校验
  → 生成新的 LifePlan
  → P0 整体校验
  → Worker 调用 P1
  → 更新最新有效结果
  → IndexedDB 原子保存
  → 广播新 revision
```

计算结果不是事实来源。刷新后先读取 `LifePlan`，再读取匹配输入哈希和版本的缓存；缓存不匹配时重新计算。

## 13. 视觉规范

### 13.1 层级

- 页面背景使用低对比度中性色。
- 内容区域使用白色或主题表面色，不为每个数字制作厚重卡片。
- 绿色只表示主要操作和正常结果。
- 琥珀色表示估算、待确认、数据过期和资金风险。
- 红色只表示删除、损坏和无法保存，不用于普通资金缺口。
- 边框优先于阴影；阴影只用于抽屉、浮层和粘性区域分离。

### 13.2 字体与数字

- 页面标题 28～36px，工作台内容标题 20～24px。
- 正文 14～16px，说明文字不小于 12px。
- 金额使用 `tabular-nums`。
- 金额与单位保持同一行，单位使用次一级颜色。
- 中文不使用全大写英文标签。
- 避免超大营销标题进入工作台。

### 13.3 间距与对齐

- 采用 4px 基础间距系统。
- 表单字段在同一网格中等高、标签基线一致。
- 桌面双列字段最小宽度 240px。
- 单个字段说明预留固定区域或放在字段下方，不因 tab 或模式切换导致相邻内容跳动。
- 所有列表金额右对齐，状态标签左对齐。

### 13.4 动效

- 标签切换只改变内容淡入，不移动左侧标题或全局布局。
- 折叠动画 160～200ms。
- 图表更新使用轻微过渡，不从零重新播放。
- `prefers-reduced-motion` 时关闭平滑滚动和位移动画。

## 17. 隐私与可靠性

## 18. 错误与恢复设计

| 场景               | 用户界面                 | 数据处理                 |
| ------------------ | ------------------------ | ------------------------ |
| Landing 输入无效   | 字段错误和首错聚焦       | 不写交接数据             |
| 交接过期           | 创建状态，可返回 Landing | 清除过期信封             |
| 交接损坏           | 说明无法读取，允许重试   | 保留原始值到本次会话结束 |
| IndexedDB 打开失败 | 本地存储不可用说明       | 不声称已保存             |
| 计划校验失败       | 恢复页面                 | 尝试最近快照             |
| 计算失败           | 显示上一次有效结果       | 不覆盖结果缓存           |
| 保存失败           | 顶部错误和重试           | 保留内存修改             |
| 多标签页冲突       | 页面内提示与恢复操作     | 不自动覆盖任一版本       |
| 备份导入失败       | 展示具体阶段             | 当前计划不变             |

所有错误必须有下一步操作。禁止出现只含“出错了”的死路页面。

### 19.5 性能预算

| 项目               |                     目标 |
| ------------------ | -----------------------: |
| 工作台首次可交互   |  本地开发基准设备 < 2.5s |

## 22. P2 完成后的页面跳转

最终主流程：

```text
Landing /
  → 填写当前年龄、个人收入、个人支出、退休年龄和计算终点
  → 查看快速结果
  → 完善我的一生账本
  → sessionStorage v2

  → 概览
  → 计划：拆分和补充
  → 自动重算与保存
  → 概览：展开逐年账本核对
```

所有修改都在 `/plan` 内完成。概览负责回答“结果是什么”，并可展开账本回答“每一年怎么算”；计划负责回答“输入是什么”。这三个问题构成 P2 的完整闭环。
