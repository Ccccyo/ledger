# 一生账本 P2.1：真实用户动线与系统分析开发设计说明

> 状态：待实现  
> 更新时间：2026-10-14  
> 适用范围：Landing、计划工作台、系统分析、方案试算  
> 前置约束：复用 `LifePlan 2.0.0` 与 P1 确定性月度计算内核
> 工程实施：`P2.1_工程实施开发文档.md`

## 1. 本文解决什么

P0/P1 已经解决了数据标准与可复现计算，P2 已经搭起本地计划工作台，但当前体验仍偏向“填参数—看结果”。真实用户并不是为了填写一张长期财务表而来，而是带着以下问题：

1. 按现在的生活继续下去，我的一生会怎样？
2. 买房、孩子、照顾父母和退休挤在一起时，钱会在哪一年最紧？
3. 现在最值得核对或调整的是什么？
4. 如果改变时间、金额或收入，结果能改善多少，代价是什么？

P2.1 将产品重构为“建立人生轨迹—看懂关键阶段—试算可控行动—核对年度账本”的闭环。用户不需要 AI，也能创建、理解、调整、试算、保存和核对完整计划。

如本文与 `P2_最小可用产品开发设计说明.md` 的页面结构冲突，P2.1 在用户动线、工作台导航、系统分析和方案试算方面优先；存储、恢复、隐私、可访问性和计算可靠性继续沿用 P2。

## 2. 不可破坏的产品合同

### 2.1 所有计算不通过 AI

以下内容只能由本地确定性代码生成：

- 收入、支出、资产、负债和存款的逐月变化。
- 收入实际增长、余额实际收益和房贷还款。
- 首次资金缺口、最低余额、期末余额和净资产。
- 年度支出构成与资金余额图表。
- 关键影响因素、规则判断和数据完整性。
- 任一行动方案调整前后的差值。
- 汇率、利率或参考数据更新后的重新计算。

相同的 `LifePlan`、计算版本和数据版本必须得到相同结果。AI 不得生成、改写或兜底任何正式金额。

### 2.2 无 AI 时产品必须完整可用

断网、未配置模型、AI 服务失败或完全删除 AI 代码时，以下流程必须全部可用：

```text
创建计划
  → 补充人生阶段与事件
  → 查看两张核心图表
  → 阅读系统分析
  → 试算行动
  → 对比并应用调整
  → 查看年度账本
  → 本地保存、备份与恢复
```

界面术语固定为：

| 名称     | 含义                             | 当前版本               |
| -------- | -------------------------------- | ---------------------- |
| 系统分析 | 确定性结果分析与固定规则         | 展示                   |
| 方案试算 | 修改计划副本后调用同一计算器对比 | 展示                   |
| 规划助手 | 用自然语言解释既有结果和协助操作 | 后续 AI，不展示入口    |
| 数据更新 | 拉取并审核外部参考数据           | 后续 Agent，不展示入口 |

系统分析区域固定说明：

> 根据你当前填写的数据和计算规则生成，不使用 AI。

### 2.3 产品不替用户做决定

系统可以描述事实、暴露冲突、给出可试算的调整，不得使用“最佳方案”“你应该”“一定够用”等确定性表达。每个行动必须同时说明：

- 为什么出现。
- 调整了哪个用户可控参数。
- 调整前后发生了什么变化。
- 可能牺牲什么。
- 尚未计入什么。

## 3. 用户、场景与成功标准

### 3.1 核心用户

25～45 岁、开始同时面对住房、伴侣、孩子、父母和退休问题的个人或家庭。用户通常只掌握大致数字，不具备专业财务知识，也不愿在第一次使用时填写几十项参数。

### 3.2 用户进入产品时的真实状态

- 有一个模糊焦虑：“现在赚得还行，但不知道以后够不够。”
- 有一个具体决定：“准备买房/生孩子/换工作，想知道扛不扛得住。”
- 有一份零散家底：“知道工资、存款和大概开销，但没有完整账本。”
- 需要的是方向和验证，不是精确到未来每一元的预言。

### 3.3 完成一次有效使用的标准

用户离开前至少能说清楚：

1. 自己的计划覆盖了哪些人生阶段。
2. 钱最紧的年龄或年份，以及主要原因。
3. 当前计划下一个值得核对或尝试的行动。
4. 该行动的试算结果与取舍。

产品成功不以“填完所有字段”为标准，而以用户形成上述四点认识为标准。

## 4. 范围与迁移决策

### 4.1 必须从旧产品迁移的产品能力

| 能力             | 迁移方式                                                 |
| ---------------- | -------------------------------------------------------- |
| 家庭长期收支骨架 | 迁移为收入、生活、住房、孩子、父母、退休、事件七类       |
| 伴侣             | 可选家庭成员，共享家庭计划；不建立独立职业模型           |
| 收入变化         | 使用用户填写的实际增长率，不预测行业或职业               |
| 住房             | 支持租房、已有房、计划买房，金额和时间由用户填写         |
| 孩子             | 支持人数、起止时间和阶段性总额，不迁移完整教育路线       |
| 父母             | 支持一笔或多笔照护支出及起止时间，不做自动阶段预测       |
| 退休             | 用户填写退休年龄、退休支出和稳定收入，不自动算养老金政策 |
| 人生事件         | 支持一次性或持续收入/支出，例如停工、装修、继承、副业    |
| 资产与债务       | 保持现金、非现金资产、债务和净资产分离                   |
| 逐年账本         | 保留年度核对能力，明细由月度结果聚合                     |
| 两张核心图表     | 年度支出构成、可用资金与净资产轨迹                       |

### 4.2 迁移但简化

| 旧能力       | P2.1 简化                                              |
| ------------ | ------------------------------------------------------ |
| 城市生活参数 | 改为用户当前生活支出；不依赖城市数据库                 |
| 教育路线     | 改为孩子阶段性支出总额或自定义明细                     |
| 配偶模型     | 只记录成员、收入和停止工作时间                         |
| 父母照护     | 默认一项持续支出，可按需追加事件                       |
| 情景比较     | 不保留顺利/一般/不顺模板，改为一次一个可解释的方案试算 |
| 假设与依据   | 放在字段和结果旁的统一抽屉，不设独立依据页面           |
| 文字解析     | 只显示当前最重要的结论；更多解释按需展开               |

### 4.3 Demo 不迁移

- 15 个城市数据库。
- 自动房价和租金。
- 完整教育路线。
- 养老金政策计算。
- 配偶独立职业模型。
- 父母多阶段照护。
- 房产出售、出租和换城市。
- 顺利、一般、不顺三情景。
- 生活档位和储蓄率对照。
- 独立依据页面。
- 完整公式审计。
- CSV 导出。
- AI 填表评测页面。
- 真实数据自动抓取。
- 多方案长期管理。

### 4.4 暂不展示

脚手架已有的聊天、AI 生成、积分、定价、登录、订阅和 API Key 页面不属于当前用户动线。未完成的规划助手和数据更新 Agent 不放灰色按钮、不标“即将上线”，避免用户误以为完成计划必须依赖 AI。

## 5. 金额与购买力口径

### 5.1 用户看到的唯一口径

工作台顶部固定显示：

> 所有金额均以当前购买力呈现。

不使用“按今天购买力计算 · 收入按实际增长率变化”这样的技术句作为主说明。详细解释放入“计算口径”抽屉：

> 为了让不同年份可以直接比较，未来金额会折算成相当于现在多少钱。收入和支出只按你填写的购买力变化计算，不另外重复加入通胀。

### 5.2 收入变化

主表单不用“名义增长率/实际增长率”术语，使用：

**收入购买力变化**

- 基本不变：`0 bps`。
- 缓慢提高：预设值，由产品配置并明确可修改。
- 持续提高：预设值，由产品配置并明确可修改。
- 自定义：输入年变化百分比。

存储和计算仍使用 `realGrowthBps`。预设只帮助填写，不是行业预测。

### 5.3 存下来的钱会变化

不能再假设“每年结余只是相加”。余额滚动必须覆盖：

```text
本月期末可用资金
  = 本月期初可用资金
  + 本月收入
  - 本月支出
  - 本月债务还款
  + 本月新增借款
  + 本月可用资金实际收益
```

为保持 Demo 简洁：

- 默认“余额实际年收益率”为 `0%`，属于保守假设。
- 在“高级假设”允许用户自行修改。
- 计算引擎按月复利，正式结果仍以当前购买力展示。
- 现金和非现金资产分开；房产升值不会自动变成可花的钱。
- 当可用资金为负时，不计算正向收益；负数如何计息必须由明确债务记录决定。

界面使用“余额实际年收益率”，说明文案为“扣除物价变化后，存款或可支配投资余额每年的变化”。不得默认承诺正收益。

### 5.4 外币与汇率

当前产品只展示 CNY，不在界面显示“外币按某月汇率折算”。未来数据 Agent 可以更新汇率参考，但必须满足：

1. Agent 只生成带来源和日期的结构化候选值。
2. 用户确认后才写入计划或数据版本。
3. 写入后仍由确定性计算器完成折算和重算。
4. 历史计划保留原数据版本，不因后台更新静默变化。

## 6. 信息架构

普通用户只接触两个路由：

```text
/       了解产品、建立第一版计划
/plan   概览、规划、年度账本
```

`/plan` 使用三个职责明确的视图：

| 视图     | 回答的问题                           | 主要内容                                             |
| -------- | ------------------------------------ | ---------------------------------------------------- |
| 概览     | 这份人生计划会怎样，我现在能做什么？ | 结论、人生轨迹、两张图、系统分析、方案试算           |
| 规划     | 我是按什么生活算的？                 | 家庭、收入、生活、住房、孩子、父母、退休、事件、假设 |
| 年度账本 | 这些数每一年是怎么来的？             | 年度汇总、分类明细、最低余额月份、追溯入口           |

桌面端为顶部标签，移动端为三项底部导航。URL 只保存 `tab`、`section`、`year` 等安全界面状态。

## 7. 真实用户主流程

### 7.1 全流程

```text
看到产品承诺
  → 用 7 个个人数据建立基线
  → 立即得到“如果不加入大事”的初步轨迹
  → 沿人生时间轴补充住房、孩子、父母、退休和其他事件
  → 每完成一组，结果即时重算并说明新增影响
  → 回到概览，看关键阶段和两张核心图表
  → 阅读最多 3 条系统分析
  → 选择一个行动进行无损试算
  → 对比改善、代价与未计入项
  → 应用调整或保留原计划
  → 到年度账本核对关键年份
```

用户任何时候都能回到概览看到已有结果，不设置“全部填完才能查看”的门槛。

### 7.2 Landing：建立第一版基线

Landing 首屏承诺：

> 把收入、生活和人生大事放到同一条时间线上，看看哪几年最紧，以及现在能做什么。

Landing 只建立个人基线，不询问家庭结构，也不填写伴侣、孩子或父母信息。首轮只有 7 个字段：

1. 当前年龄。
2. 起始可用资产估算，以“万”为录入单位，只含可用于长期规划的存款和现金。
3. 自己当前的税后月收入。
4. 自己工作期的每月支出。
5. 退休后每月需自付，即扣除预计养老金等稳定退休收入后仍需自己承担的金额。
6. 计划退休年龄。
7. 计算到多少岁。

Landing 不填写非流动资产、债务、城市、住房、教育路线、养老金政策、汇率或投资品类。快速估算从用户填写的起始可用资产开始，退休前使用个人收入与工作期支出，退休后个人收入按 0 处理、支出使用用户填写的每月需自付金额。结果区域必须直接说明这一口径，进入工作台后再补充可单独追溯的资产、退休收入与支出。

提交后在同页展示：

- 条件式一句话结论。
- 首次资金缺口。
- 期末可用资金。
- “这只是基于个人起始资产与当前收支、尚未加入住房和其他人生大事的基线”提示。
- 主操作“加入我的人生大事”。

用户获得的不是一个最终答案，而是一张可继续完善的底稿。

### 7.3 初次进入工作台：补齐人生轨迹

第一次进入 `/plan` 时，不直接把用户扔进九个折叠表单。概览顶部显示“你已经有一条基础轨迹”，下方给出五个时间节点：

```text
现在 → 住房 → 伴侣 - 孩子 → 父母 → 退休
```

每个节点只有三种状态：

- 未填写：浅色描边，“暂未计入”。
- 已填写：显示年龄、金额和一句摘要。
- 不适用：显示“当前不考虑”，仍可恢复。

用户可以按现实顺序补充，也可以跳过。每完成一个节点：

1. 生成新的 `LifePlan`。
2. 调用同一个 P1 计算器。
3. 保存结果。
4. 返回该节点对首次缺口、最低余额和期末余额的差值。
5. 用一句话反馈，例如“加入 32 岁购房后，最低余额提前了 4 年”。

### 7.4 日常回访

已有计划的用户直接进入概览，顶部显示最近保存时间和当前口径。用户通常从三种动作开始：

- 看“从上次修改后发生了什么”。
- 修改一项现实数据。
- 重开上次未应用的方案试算。

P2.1 不依赖后台真实数据，因此不存在自动变化的正式结果。只有用户修改或确认数据更新后才重新生成结果。

## 8. 概览页面设计

概览采用纵向叙事，不使用密集卡片仪表盘。内容顺序固定为：

1. 当前结论。
2. 你的人生轨迹。
3. 两张核心图表。
4. 系统分析。
5. 可以尝试的行动。
6. 数据完整性与口径。

### 8.1 当前结论

标题始终以条件表达开头：

- “按照当前计划，资金在 52 岁前保持为正，购房后的三年最紧。”
- “按照当前计划，61 岁首次出现资金缺口，主要发生在停止工作之后。”
- “按照当前计划，期间会短暂出现缺口，但之后恢复为正。”

标题下显示三个摘要，不制作四个等权 KPI 卡：

- 最紧时点与最低可用资金。
- 期末可用资金。
- 期末净资产。

可用资金与净资产必须并列解释，避免“有房但没现金”被误读为有钱可花。

### 8.2 你的人生轨迹

按年龄横向展示关键事件，移动端改为纵向：

```text
28 岁 现在
32 岁 计划购房 · 首付 80 万
34 岁 孩子出生 · 支出开始
45 岁 父母支持 · 每月 3,000 元
60 岁 停止工作
```

时间轴不是装饰导航。点击节点直接进入对应规划字段，且每个节点展示它对该年现金流的净影响。

### 8.3 两张必须展示的图表

#### 图一：每年花多少

- 年龄或年份作为横轴。
- 日常生活、住房与贷款、孩子、父母、其他、退休为堆叠项。
- 退休年龄使用清晰参考线。
- 默认只标注金额突变的关键年份，避免每根柱子都显示文字。
- 点击某年打开年度详情。
- 图下给出一句事实摘要，例如“支出最高出现在 32 岁，主要来自购房首付”。

#### 图二：资金能否撑住

- 主线：可用资金。
- 辅助虚线：净资产。
- 零线必须明显。
- 标出首次缺口、最低点和退休时点。
- 不使用大面积风险红色；缺口区使用克制的琥珀色。
- 图下给出一句事实摘要，例如“现金在 52 岁转负，但净资产仍为正，属于流动性缺口”。

两张图都必须提供可访问表格替代。Tooltip 金额、年龄和分类名称来自同一年度结果，不在组件内重新计算。

### 8.4 不默认展示的解析

以下内容不占据概览主视觉：

- 每条公式的推导。
- 所有年份的文字说明。
- 低影响敏感性结果。
- 完整假设清单。
- 通用理财科普。

它们进入年度账本、统一依据抽屉或未来规划助手的问答内容。主界面只保留会改变用户理解或下一步行动的信息。

## 9. 系统分析：不是 AI 的建议

### 9.1 生成管线

```text
LifePlan
  → P1 月度计算
  → 事实提取器
  → 规则匹配器
  → 候选行动生成器
  → 使用同一 P1 计算器重算候选计划
  → 排序与去重
  → 最多展示 3 条系统分析和 3 个行动
```

禁止把大模型输出写入这条管线。

### 9.2 系统分析的数据结构

```ts
type InsightSeverity = 'info' | 'attention' | 'gap';

interface PlanInsight {
  id: string;
  ruleId: string;
  severity: InsightSeverity;
  titleKey: string;
  bodyKey: string;
  evidence: Array<{
    metric: string;
    value: number | string;
    traceIds: string[];
  }>;
  relatedInputIds: string[];
  occurredAtMonth?: number;
}

interface ActionCandidate {
  id: string;
  ruleId: string;
  titleKey: string;
  reasonInsightId: string;
  patch: PlanPatch;
  adjustableFields: string[];
  tradeoffKey: string;
  baselineInputHash: string;
}

interface SimulationComparison {
  baseline: ResultDigest;
  candidate: ResultDigest;
  delta: ResultDigest;
  candidatePlan: LifePlan;
  calculationVersion: string;
}
```

`PlanPatch` 必须是白名单结构，不允许任意路径写入。行动候选只存在内存中，用户点击“应用到计划”后才写入正式计划。

### 9.3 第一版规则表

| 事实条件                           | 系统分析                                 | 可试算行动                                   |
| ---------------------------------- | ---------------------------------------- | -------------------------------------------- |
| 首次缺口发生在购房前后 12 个月     | 购房支出是当前最早缺口的主要触发因素     | 推迟 1～3 年、降低总价或提高首付三选一试算   |
| 购房与孩子支出在 24 个月内重叠     | 两项大额支出集中在同一阶段               | 调整其中一个时间点，展示对最小余额的影响     |
| 可用资金为负但净资产为正           | 当前问题是可动用资金不足，不是总资产为负 | 降低一次性支出或增加现金缓冲试算             |
| 停止工作到稳定退休收入之间存在缺口 | 退休过渡期没有足够持续收入               | 推迟停止工作年龄或补充该阶段收入试算         |
| 退休支出是前三大影响因素           | 结果对退休生活支出较敏感                 | 以当前值上下 10% 试算，不直接建议削减        |
| 当前结余长期为正但余额收益率仍为 0 | 已按保守方式处理余额增长                 | 提醒用户核对高级假设，不自动填正收益         |
| 某关键分类仍为总额估算             | 当前结论依赖一笔未拆分总额               | 引导补充住房、孩子或退休明细，不生成金额建议 |
| 无缺口且关键资料完整               | 当前计划在已填范围内可持续               | 提醒保存基线，并试算最关心的一件人生大事     |

“主要触发因素”必须由移除该事件或微调该参数后的确定性重算验证，不能只按金额大小猜测。

### 9.4 排序原则

最多展示三条，依次考虑：

1. 是否解释首次缺口或最低点。
2. 用户是否能直接控制对应参数。
3. 重算后的改善幅度。
4. 是否与已展示内容重复。
5. 数据是否完整到足以支持该结论。

若数据不足，优先显示“需要核对什么”，不显示看似精确的行动。

### 9.5 文案格式

每条系统分析固定四段：

```text
发生了什么
为什么：引用具体年龄、事件和金额
可以尝试：一个可控变化
查看依据 / 去试算
```

禁止使用“AI 建议”“智能推荐”“准确率”“成功概率”。

## 10. 方案试算交互

### 10.1 入口

入口只来自：

- 系统分析后的“试算这个调整”。
- 规划字段旁的“试试别的时间/金额”。
- 概览固定的“新建一次试算”。

### 10.2 试算面板

桌面端右侧抽屉，移动端全屏。内容顺序：

1. 要改变什么。
2. 当前值与试算值，可编辑。
3. 调整理由。
4. “重新试算”操作。
5. 结果对比。
6. 代价与未计入项。
7. “应用到计划”与“放弃试算”。

结果对比只展示真正变化的指标：

| 指标         | 当前计划 | 试算后 |       变化 |
| ------------ | -------: | -----: | ---------: |
| 首次缺口     |    52 岁 |  55 岁 |  推迟 3 年 |
| 最低可用资金 |   -48 万 | -12 万 | 改善 36 万 |
| 期末可用资金 |   -96 万 | -43 万 | 改善 53 万 |

同时显示一条取舍，例如“购房时间推迟 2 年”。改善不是推荐，用户必须主动应用。

### 10.3 状态规则

- 试算基于计划副本，编辑不会触发正式自动保存。
- 每次修改候选值都经过 P0 校验和 P1 重算。
- 正式计划在试算期间变化时，候选标记为过期并要求重新生成。
- 试算失败保留上一次有效对比，不得清空正式结果。
- P2.1 一次只保留一个临时试算，不形成多方案管理。

## 11. 规划视图

规划不是长问卷，而是与人生时间轴一致的可编辑清单：

1. 我们是谁：年龄、成员、规划终点。
2. 现在的家底：可用资金、资产、债务。
3. 收入与工作：本人/伴侣收入、购买力变化、停止工作时间。
4. 日常生活：工作期与退休期日常支出。
5. 住房：租房、已有房或计划购房。
6. 孩子：人数、开始时间、阶段性支出。
7. 父母：支持金额与起止时间。
8. 退休：个人需承担支出、稳定收入。
9. 其他人生事件：一次性或持续收入/支出。
10. 高级假设：余额实际收益率等少量全局参数。

每个折叠项关闭时展示一句真实摘要，例如：

> 32 岁购房 · 首付 80 万 · 贷款 20 年

而不是“已填写 4/6 项”。

字段编辑后，页面先显示局部校验，再计算，再给出结果变化提示。结果变化提示描述事实：

> 这次修改让最低可用资金减少了 18 万，首次缺口提前到 50 岁。

该提示来自新旧结果差值，不属于系统建议。

## 12. 年度账本

年度账本承担“核对”，不承担产品主叙事。默认列：

- 年龄 / 年份。
- 收入。
- 日常生活。
- 住房与贷款。
- 孩子。
- 父母。
- 其他。
- 年度净结余。
- 年末可用资金。
- 年末净资产。

默认聚焦以下年份：当前年、重大事件年、退休年、首次缺口年、最低余额年。用户可以展开全部年份。

点击某年打开详情抽屉，展示当年 12 个月聚合、分类项目、最低余额月份和来源追溯。不得在账本组件内复制任何计算公式。

## 13. 视觉与交互方向

工作台模式为 **Operate**：优先保证理解、编辑与核对，而不是营销表现。

### 13.1 视觉原则

- 延续中性背景、克制绿色和琥珀风险色。
- 使用大段留白、分隔线和明确标题形成“人生账本”感。
- 不把每个数字放进独立圆角卡片，避免通用 SaaS 仪表盘感。
- 主视觉焦点是结论、人生轨迹和资金转折，不是组件数量。
- 数字使用等宽数字特性，金额单位保持同一行。
- 红色只用于删除、数据损坏和不可恢复错误，不用于普通缺口。

### 13.2 操作反馈

- 修改后的重算使用 300～500ms 防抖。
- 图表更新保留坐标系，只平滑更新线和柱，不从零播放。
- 应用试算后，在原位置给出“已应用，可撤销”的短时反馈。
- 所有保存、计算和试算状态使用明确文字，不只使用转圈图标。
- `prefers-reduced-motion` 下关闭位移和曲线动画。

### 13.3 响应式

- `< 640px`：人生轨迹纵向、图表支持横向查看但关键结论不依赖拖动、年度表改列表、试算全屏。
- `640～1023px`：两列表单、顶部标签、覆盖式抽屉。
- `>= 1024px`：三标签、宽图表、右侧试算与依据抽屉。
- 主要点击区域不小于 44 × 44px。

## 15. 数据流

```text
用户编辑正式字段
  → P0 字段与整体验证
  → P1 月度计算
  → 正式结果摘要
  → 事实提取与系统分析
  → IndexedDB 保存正式计划

用户打开方案试算
  → 复制当前 LifePlan
  → 应用白名单 PlanPatch
  → P0 验证候选计划
  → P1 计算候选结果
  → 生成基线/候选差值
  → 用户确认后替换正式计划
```

系统分析是正式结果的派生数据，不写入 `LifePlan`。可以按 `inputHash + calculationVersion + analysisVersion` 缓存，但缓存失配时必须重新生成。

## 16. 后续 AI 与 Agent 的接入边界

### 16.1 规划助手

未来规划助手只能：

- 解释已经存在的系统分析和计算结果。
- 根据用户自然语言提出一个结构化 `PlanPatch` 草案。
- 调用方案试算接口获取确定性结果。
- 回答“为什么”和“如果怎样”的问题。

它不能：

- 直接返回正式金额作为计算结果。
- 绕过 P0 校验或 P1 计算。
- 未经预览和确认修改正式计划。
- 把模型推测冒充用户输入或外部事实。

### 16.2 数据更新 Agent

未来数据 Agent 只能输出候选参考记录：

```ts
interface DataReferenceCandidate {
  field: string;
  value: number | string;
  unit: string;
  region?: string;
  effectiveAt: string;
  sourceUrl: string;
  fetchedAt: string;
}
```

审核或用户确认后写入数据版本，再由 P1 重新计算。Agent 失效时，用户仍可手动维护所有正式输入。

## 17. 开发顺序

### P2.1-A：导航与人生轨迹

- 将工作台调整为概览、规划、年度账本三个视图。
- 从计划事件生成统一人生轨迹。
- 点击轨迹节点可跳到规划字段或年度详情。

验收：用户能从概览找到每个重大人生事件对应的输入和结果年份。

### P2.1-B：两张核心图表

- 实现年度支出堆叠图。
- 重构资金图为可用资金与净资产双线。
- 增加关键点标注、事实摘要和表格替代。

验收：图表值全部来自 P1 年度聚合，组件无金额计算。

### P2.1-C：确定性系统分析

- 增加事实提取、首批规则、证据和排序。
- 系统分析明确标注“不使用 AI”。
- 缺数据时优先生成核对提示。

验收：固定 fixture 对应固定 insight ID、证据和顺序。

### P2.1-D：方案试算

- 实现白名单 patch、候选计划、重算和差值。
- 实现试算抽屉、应用与放弃。
- 正式计划变化时使候选过期。

验收：未点击应用时不改变 IndexedDB；应用后结果等于直接修改正式字段的结果。

### P2.1-E：购买力与余额增长表达

- 统一当前购买力文案。
- 主表单加入收入购买力变化选项。
- 高级假设加入余额实际年收益率。
- 删除用户界面的固定汇率月份文案。

验收：0% 与正/负实际收益率均有确定性测试，未来金额不重复加入通胀。

### P2.1-F：收尾与质量

- 补齐空状态、错误、过期、撤销和移动端。
- 完成中英文文案与可访问性。
- 隐藏未完成 AI/Agent 入口。
- 运行计算回归、组件测试和端到端测试。

## 18. 测试与放行

### 18.1 系统分析单元测试

- 同一输入产生同一 insight 和 action 顺序。
- 购房导致首次缺口时命中正确规则。
- 购房与孩子不重叠时不产生重叠分析。
- 现金为负、净资产为正时识别流动性缺口。
- 数据不完整时不产生过度精确行动。
- 所有 action patch 都能通过白名单校验。
- 重算改善值等于候选结果减基线结果。

### 18.2 核心计算回归

- 余额实际收益率为 0 时保持现有 fixture。
- 正收益、负收益、余额转负和重新转正的月度顺序正确。
- 房产价值变化不进入可用资金。
- 收入实际变化与当前购买力口径不重复计算通胀。
- 所有图表和系统分析只消费正式计算结果。

### 18.3 端到端场景

1. 单身用户建立基线，加入购房后看到首次缺口与行动试算。
2. 伴侣用户加入孩子与父母支出，看到事件重叠和支出峰值。
3. 有房但现金不足的用户看到流动性解释，而不是笼统“资产为正”。
4. 用户推迟购房两年，预览对比后应用，刷新仍保持新计划。
5. 用户放弃试算，正式计划和保存 revision 不变。
6. 无网络和无 AI 配置时完成全部主流程。
7. 手机端完成创建、补充事件、试算、应用和账本核对。

### 18.4 放行清单

- [ ] 所有正式数字都可追溯到 P1 计算结果。
- [ ] 产品中没有“AI 建议”字样。
- [ ] 系统分析明确说明不使用 AI。
- [ ] 未配置 AI 时没有缺失功能或死路入口。
- [ ] 用户能看到自己的人生轨迹，而不只是参数列表。
- [ ] 两张核心图表在概览直接展示。
- [ ] 每条行动都能展示依据、改善、代价和未计入项。
- [ ] 试算不经确认不会修改正式计划。
- [ ] 当前购买力口径清晰，界面不展示固定汇率月份。
- [ ] 余额增长进入确定性计算且默认值保守透明。
- [ ] Demo 排除项没有重新进入普通用户界面。

## 19. 完成后的用户收获

产品不承诺替用户规划人生。它交付的是一条可理解、可修改、可核对的行动轨迹：

```text
我现在在哪里
  → 哪些人生大事已经计入
  → 哪个阶段最紧
  → 是现金问题还是总资产问题
  → 哪些参数真正影响结果
  → 我可以先试哪一个变化
  → 这个变化改善多少，又牺牲什么
```

这条链路即使没有 AI 也完整成立。未来 AI 的价值是降低表达和操作成本，而不是成为计算正确性或产品可用性的前提。
